# Cairn 标签系统设计方案

> 2026-10-02 粒度修订：宽主题与具体主题共用规范身份，卡片突出内容重点，导航独立收纳。当前采用的变化见 [标签粒度与导航](tag-granularity.md)。本文保留 2026-09-30 初版设计作为背景；涉及粒度与默认展示的冲突以修订文档为准。

本文提出一套适合个人收藏库、能够利用 Jev 独立判断能力的标签系统。默认分类和检索由系统标签提供，用户能够直接纠正这些标签；自定义标记完全可选。每个标签有稳定身份，每次有效修改有可追溯记录，为后续改进词表和分类策略提供依据。

方案日期为 2026 年 9 月 30 日，状态为待实施设计。本文整合前面的产品讨论、真实收藏审阅和现有代码核查，不表示功能已经上线。历史候选文件保持原样，用于追溯设计依据；本文中的最终取舍优先于其中的初稿建议。

## 一 主要设计决定

1. 日常界面默认使用两组系统标签：主题和资源类型。它们可以多选，也可以为空。
2. 系统标签足以独立支持分类、浏览、搜索和导出，不要求用户建立自定义标记或逐条确认。
3. 用户可以增删、替换、确认系统标签。这属于分类纠正，不会把系统标签变成自定义标签。
4. 自定义标记用于额外组织和记忆，初版只由用户操作，不参与 Jev 自动判断。
5. 方法、案例、观点、数据保留为次要内容属性，不占据默认标签栏；是否扩大使用由实际检索收益决定。
6. 可引用、素材、背景不作为默认自动标签；待试、已采用、我反对等个人决定不会由 AI 猜测。用户需要时可以自行标记。
7. AI 建议、人工决定和当前有效结果分别保存。人工决定优先，AI 再分类不覆盖用户纠正。
8. 人工操作按标签增量保存。移除一个标签不确认其他标签，也不冻结整个维度。
9. 标签名称、语义定义和收藏上的归属都有明确身份与版本。历史不可通过覆盖当前值冒充。
10. 使用修改记录辅助优化，但不把未修改、模糊删除或自定义标记直接当作模型正确答案。

一条写真 Skill 收藏的体验应很直接：系统自动给出“图像生成”和“Skill”，用户立即可以通过这两个条件找到它。若误加了“AI编程”，用户移除这一项，其他标签继续自动更新；如果之后手动加上“视频制作”，它仍是系统主题，只是这次归属由用户决定。用户无需创建任何自定义标记。后台分别记录自动判断、这两次人工决定与有效结果，普通页面只展示当前结果和可选的历史入口。

## 二 设计依据和适用范围

2026 年 9 月 30 日的只读审阅覆盖当前数据库中全部 45 条收藏，其中 42 条有存档正文，3 条缺少正文。收藏时间范围为 2026 年 8 月 27 日至 9 月 27 日。主要重复出现的任务是 AI 实操、内容创作、界面设计和信息整理。

这一依据只覆盖仍在当前库中的收藏，不代表已删除或未导入的历史内容。初稿的逐条归类是本次分析的建议，不是用户确认结果，也不是 Jev 分类质量评测。正文中的产品能力和效果属于原作者主张，标签不表示系统验证或认可这些主张。

历史讨论强调封闭词表、实体分离和按检索需求修订；本方案保留这些原则，取消机械的主题数量要求与主题、形态、用途的固定组合。系统不会为了填满字段，给每条收藏强行安排一个抽屉。

## 三 用户看到的标签结构

### 系统主题

主题回答“这条收藏实质讨论什么任务或领域”。采用定制、有限的候选表，不要求覆盖所有零散兴趣。以下 12 个主题作为第一版起点。

| 稳定词条 ID | 显示名称 | 纳入范围 | 重要排除边界 |
| --- | --- | --- | --- |
| ai_coding | AI编程 | AI 辅助开发、代码审查、调试、重构和专门的编程环境 | 仅用 Codex 做图、写作或运行其他任务不算 |
| agent_workflow | Agent配置与自动化 | 上下文、长期指令、工具接入、会话配置和任务自动化 | 只是发布一个面向写作或生图的 Skill 不算 |
| image_creation | 图像生成 | 生图、图像编辑、写真复拍、人物一致性和文章配图 | 普通图片展示、网页 UI 和视频动画不直接归入 |
| video_creation | 视频制作 | 视频生成、动画、分镜、B-roll、录屏和剪辑 | 网页加载动效和微交互组件归界面设计 |
| writing_creation | 写作与文风 | 文章、小说、文风复用、去 AI 腔和表达方法 | 材料是一篇长文或仅涉及版式不算 |
| ui_design | 界面设计 | 网页和 App 的视觉、交互、设计规范、组件和微交互 | 写真生成和普通产品发布不算 |
| knowledge_workflow | 信息采集与知识库 | 文章或聊天记录的采集、导出、归档、检索和复用 | 单纯推荐社区入口或偶然提及 RAG 不算 |
| information_sources | 信息源 | 持续信息来源、社区、站点、素材入口的筛选和导航 | 单个工具发布或资料库的检索实现不算 |
| model_practice | 模型训练与部署 | 训练、微调、量化、部署和推理性能取舍 | 普通云端 AI 使用和提示词文风蒸馏不算 |
| creator_business | 内容运营与变现 | 账号定位、选题增长、分发、商单和创作者接单 | 一般写作技巧、软件星标致谢和证券投资不算 |
| finance_resources | 投资理财 | 行情、回测、资产配置、金融学习和金融平台开户资源 | 接单收入与内容商单归内容运营与变现 |
| document_layout | 文档与公文排版 | Word、WPS、DOCX、公文版式、模板和格式保真 | 表达方法、网页 UI 和训练用 PDF 提取不直接归入 |

与初稿相比，“信息源与资源导航”显示名称收敛为“信息源”，“投资与金融资源”收敛为“投资理财”。这两项仍处于未激活设计阶段；实施前需要重新核对定义与对应收藏，不把初稿匹配数量当作新定义的评测结果。

主题允许合理交叉。例如介绍本地生图量化权重的收藏，可以同时属于图像生成和模型训练与部署。若两项总是同步出现且没有独立筛选价值，应修订词表，而不是靠代码硬裁掉其中一项。

单条公文排版收藏仍值得保留专门主题，因为它对应明确的检索任务。逆向安全、服饰、成人账号资源等低频主题暂不进入主候选表，但相关收藏保留在全库和全文检索中，用户也可以手动使用自定义标记。

### 系统资源类型

资源类型回答“这里介绍或提供什么可以拿来使用的资源”。它不等于来源载体，也不等于作者在论证什么。

| 稳定词条 ID | 显示名称 | 判断范围 | 不足以匹配的情况 |
| --- | --- | --- | --- |
| skill | Skill | 明确介绍或提供可安装、可复用的 Agent 技能包 | 只讨论 SKILL.md 配置文件或泛泛提到技能 |
| prompt | 提示词 | 给出可复用指令、模板，或明确提供提示词集合入口 | 只说 AI 可以完成某项工作 |
| software | 软件与服务 | 可运行软件、CLI、插件、浏览器工具或 API 服务 | 把任何开源链接都当成软件；纯观点或单独的 Skill |
| component | 代码组件 | 可复用 UI、动画或交互代码组件和组件库 | 普通设计图片、设计规范或视频动画 |
| model | 模型资源 | 模型权重、明确的训练实现、适配器或可运行模型项目 | 只介绍某个云端模型能力，或只引用模型名 |
| reference | 参考资料 | 明确可复用的规范、指南、模板、素材库或资源导航 | 仅因为它是一篇文章，或泛泛认为值得参考 |

同一条可以有多个资源类型，例如一个项目同时提供软件和 Skill。没有明确资源时可以为空。资源标签描述收藏中的介绍，不承诺外链仍可用、项目已安装或产品能力已验证。

“合集”只是组织形式，不能覆盖其中的实际资源类型。例如十个 Skill 的合集，仍然标 Skill；资源集合特征可以留在次要属性或标题中。来源“X、公众号、网页”继续使用来源字段；单帖、续帖、外链文章继续使用现有来源结构信息。

### 次要内容属性和自定义标记

方法、案例、观点、数据在需要时参与高级筛选，默认详情折叠。初版复用现有内容属性，不新增一套与资源类型重复的“工具”标签。

自定义标记没有强制结构，可以用于项目、个人记忆或实践状态。用户不创建任何自定义标记时，这一组不占据空白栏目，也不影响保存、分类、检索或导出。初版不配置自动归属规则、不让 Jev 创建新标记、不把自定义标记偷偷写入系统主题。

## 四 日常使用和页面行为

### 默认流程

用户收藏链接后，系统保存链接并沿用现有流程存档来源、生成阅读辅助和自动分类。能够直接阅读和搜索已有内容，不要求等待所有阶段完成，不要求填写收藏原因或确认标签。

列表默认展示系统主题和资源类型。视觉上可以在同一行，但能辨认分组。显示数量是界面限制而不是数据限制：优先展示通常最有用的少量标签，其余显示“还有 2 个”，详情和导出保留全部有效标签。排序需要确定性，不能每次刷新随机变化。

用户编辑时使用“添加标签”搜索已有标签。结果区分系统主题、资源类型和已有自定义标记；只有在找不到合适项时，才提供“创建自定义标记”。新增标记后直接回到收藏，不强迫建立分类树或管理页面。

通过验证的策略自动采用明确匹配的标签，它们立即参与浏览、筛选和导出，不依赖用户确认。处于不确定区间的候选放在详情的“其他建议”中，默认不属于有效标签；用户采用后才进入当前结果。普通卡片不展示满屏待确认提示。

标签文字用于查看或筛选，独立的移除按钮用于删除当前归属，避免点击整块标签就误删。手机触控、键盘和辅助阅读工具均应能区分这两个动作。

### 来源提示和编辑反馈

当前标签可以显示“自动标签”“你已确认”或“你添加”。“系统标签”表达的是受控词表身份，“自动标签”表达的是本条归属来源，二者不能混为一个字段。详情中的“其他建议”专指尚未自动采用的边界候选，不与有效标签共用同一状态。

用户只修改一个标签时，其余标签仍保持自动状态。不能因为单条发生过一次人工操作，就把全部标签显示为已确认。用户只修改收藏原因、阅读状态或备注，也不会确认标签。

移除标签立即更新当前结果，提供一次普通撤销入口，不为单个移除增加确认对话。已排除的 AI 标签放在编辑器或历史中，日常卡片不永久展示一排划线标签。整体清空或批量操作需要显示实际影响范围。

“查看变更”按时间显示谁做了什么。模型概率、版本和运行记录放在可展开详情，不进入普通用户的必经操作。理由可以选填，不能变成每次整理的负担。

### 展示偏好和排除标签

在收藏编辑器中移除标签，表示不希望这条收藏继续带有该标签，会影响筛选和导出。用户只是不想在列表看到资源类型时，应使用全局展示偏好；该操作不会改变归属，也不会形成负面分类样本。

卡片因空间不足折叠标签同样不产生任何拒绝、清空或确认事件。展示与分类必须分开。

### 状态表达

| 情况 | 用户可见信息 | 处理规则 |
| --- | --- | --- |
| 分类尚未运行或排队中 | 标签处理中 | 保留已有人工标签，正常阅读和搜索 |
| 缺少可判断的来源 | 暂无足够内容判断标签 | 不按作者名、产品名或备注猜主题，允许人工添加 |
| 正文不全但有可信标题或片段 | 标签仅依据标题或现有片段 | 有充分证据的标签可以生效，保留证据范围，不借 URL 或旧摘要补充事实 |
| 已判断且没有适合的标签 | 暂无匹配标签 | 这是有效结果，不标红、不强迫新建标签 |
| 某些判断不确定 | 详情中显示可选建议 | 已确定标签正常生效，不把整条变成失败 |
| 分类服务失败 | 标签暂未更新，可重试 | 阅读内容、旧结果和人工修改继续保留 |
| 来源或定义发生变化 | 已有人工标签，内容或定义已更新 | 保留用户决定，提示其依据版本，不静默改写 |

这些状态必须来自实际记录，不能仅用“标签数组为空”推断。来源获取失败、阅读辅助失败和分类失败保持各自状态，单独重试分类不重新抓取来源。

## 五 搜索和筛选

普通关键词覆盖标题、存档正文、摘要、现有实体和备注等已有可搜索内容。标签补充筛选，不承担全部检索责任。

筛选提供主题、资源类型和可选自定义标记。每组内多个选择默认表示任一个匹配，跨组要求同时匹配。例如选择图像生成，以及 Skill 或提示词，表示查找图像生成相关的这两种资源。

需要同组全部匹配时，作为明确的高级选项提供，不能悄悄切换查询语义。计数基于服务端完整筛选结果和当前有效归属，不依据当前页面加载数，也不把被人工排除的 AI 标签算进去。

默认“全部收藏”包含没有标签的内容。提供无系统标签、分类处理中、存在人工纠正等入口，但不把它们都叫作“待确认”。已有自定义标记才显示相关筛选，用户完全不用这一组也能完成全部默认任务。

导出包含全部有效标签、分组和归属来源；历史导出是单独能力，必须标明覆盖区间。正常导出不确认标签，不改变收藏状态，也不调用模型。

## 六 标签身份和词表管理

### 两种身份

标签定义身份解决“这个标签是什么”；收藏与标签的归属身份解决“这个标签为何出现在这里”。

系统标签逻辑身份由命名空间、维度和稳定词条 ID 组成，可以复用当前的维度加词条 ID。自定义标记使用所有者加独立 ID。外部 API 可以封装为稳定 tag_ref，不要求把显示名称当作主键，也不要求为已有词条重新分配随机 ID。

例如 `system/topics/image_creation` 与 `system/resource_kinds/skill` 是不同身份；`custom/<owner>/<id>` 属于可选标记。路径形式只是设计示例，实现可使用等价的不透明 ID。内部保存归属时，以收藏 ID 加标签身份唯一定位，不需要为重复添加产生多个关系。

显示改名、别名索引和定义查找也必须使用完整身份。不同维度可能复用 `method` 等词条 ID，不能仅按裸 `term_id` 保存全局改名，否则改一个维度会覆盖另一个维度。

### 标签定义记录

每个定义至少包含稳定身份、分组、显示名、别名、语义定义、正反例、显示修订、定义版本和状态。系统词表继续以版本化配置为权威，自定义定义按当前账户保存，不额外建一个与配置竞争的系统真相。

标签的创建者、定义类型和当前归属的操作者分别保存。用户采用系统标签，不改变其系统身份；AI 第一次建议的标签后来被人工确认，也仍能追溯原始建议。

### 同名和近义冲突

| 冲突 | 规则 |
| --- | --- |
| 自定义名称命中已有系统标签名称或别名 | 优先提供使用已有系统标签，不静默创建第二个同义标记；已停用项说明状态并推荐替代项 |
| 用户坚持表达不同含义 | 要求使用能区分的名称，例如“我的图片项目”；不会自动共享系统定义 |
| 同一用户创建重复自定义名称 | 归一化后复用已有项，不产生重复身份 |
| 名称近似但未确定同义 | 给出参考建议，用户仍可创建；不能用模型相似度自动合并 |
| 历史已有同名标签 | 保留原身份和事件，界面附分组或来源消歧，提供明确整理入口 |

名称归一化复用现有大小写、空白和全角处理，不能把所有模糊近义词自动折叠。系统别名必须显式维护。

### 改名 语义变化 合并和停用

- 改显示名只增加显示修订，稳定身份、原始判断和人工归属不变。历史保留当时名称，当前页面可使用现名。
- 判定边界变化增加定义版本，并生成新的问题身份。历史记录继续按旧定义解释；旧人工决定保留并带上其适用版本，不自动当作新定义的评测答案。
- 彻底改变概念含义时创建新身份，通过显式关系记录相关、上下位或拆分，不借改名复用旧含义。
- 合并仅用于经确认的同义标签，记录来源、目标、定义版本、影响范围和合并事件。历史仍保留原始身份，查询通过明确映射处理。
- 若同一收藏对来源标签的最新有效人工态度冲突，例如采用 A 而排除 B，不直接搬成目标标签 C 的采用或排除。该收藏暂不启用合并映射，仍按原身份展示、筛选和导出，筛选 C 不会经 A 或 B 隐式命中；不能让新目标的自动建议绕过冲突。保留旧决定、标记待处理，用户明确处理后才完成迁移。迁移产生的关系标明迁移来源，不冒充用户直接确认了 C。
- 停用表示不再供新自动判断和新添加选择。已有有效归属与历史查询保留，并显示已停用；用户仍可移除这些归属。
- 删除单条收藏上的标签不等于删除词表定义。系统词表变更属于独立管理入口；自定义标记的全库移除也需要显示关联收藏数量。

## 七 AI 建议 人工决定和有效结果

### 三层数据

1. AI 建议层：保存每次 Jev 运行的原始判断、使用的来源与问题版本、策略决定和自动建议，人工编辑不覆盖它。
2. 人工决定层：记录用户对指定标签的采用、确认、排除、恢复自动等决定，以及自定义标记的操作。
3. 当前有效层：按照确定规则合并，供列表、筛选、详情和导出使用；它可以重建，不是历史事实的唯一来源。

策略结果必须明确区分自动采用、仅供建议和不采用，可以使用 `include / review / exclude` 等等价状态。只有自动采用进入自动有效层；仅供建议保留在候选区，默认不参与标签筛选、计数和普通导出，用户明确采用后才生效。人工排除是另一层决定，不与策略不采用混淆。

对某条收藏的某个系统标签，人工状态可以是跟随自动、人工采用或人工排除。在没有组级自动屏蔽时，其有效归属遵循下表。

| 人工状态 | 当前策略是否自动采用 | 是否为有效标签 |
| --- | --- | --- |
| 跟随自动 | 是 | 是，显示自动标签 |
| 跟随自动 | 否 | 否 |
| 人工采用 | 是或否 | 是，保留人工采用或确认身份 |
| 人工排除 | 是或否 | 否，排除决定保留 |

当来源更新时，人工决定仍保留，页面标记依据已变化。系统不会把保存的旧接受伪装成用户对新内容的确认。没有人工决定的标签可以随新分类变化，自定义标记不受 AI 运行影响。

### 明确清空与逐标签移除

逐标签移除只排除该标签。即使用户把当前可见标签逐个移除，也不会自动推断“整个维度永远都不适用”；将来新出现且未被操作的标签仍可进入。

“这一组都不适用”是单独的高级动作，范围必须清楚：它建立维度级明确空决定，阻止该组 AI 自动新增。页面显示“已手动清空”，同时提供恢复自动。用户后续采用个别标签时，只加入这些标签，不能因此复活整组自动候选。

明确清空会重置该组当前逐标签覆盖，历史仍保留。随后可以人工采用某项，也可以只对某项恢复自动：前者固定保留该项，后者仅允许该项跟随最新 AI；其他未操作项继续被组级屏蔽。存在例外后，页面改为“已关闭本组自动新增”，不再声称这一组仍为空。整组恢复自动才解除屏蔽与该组全部逐标签覆盖。

默认编辑器不使用整组替换式提交。“确认当前标签”仅确认用户实际看到并选中的标签，不代表排除其他未显示、未判断或以后新增的候选。

## 八 编辑动作和撤销规则

| 操作 | 写入行为 | 后续 AI 再分类 |
| --- | --- | --- |
| 添加已有系统标签 | 为该标签追加人工采用 | 保留用户采用 |
| 确认 AI 标签 | 为所选标签追加确认并采用 | 保留确认，不确认其他标签 |
| 移除系统标签 | 为该标签追加人工排除 | 不自动加回该标签 |
| 替换 A 为 B | 同一操作内原子排除 A、采用 B，记录替换关系 | 保留这次人工决定 |
| 单标签恢复自动 | 撤销该标签当前人工覆盖，追加恢复事件 | 使用最新 AI 建议，可能仍无标签 |
| 整组恢复自动 | 仅重置指定组的覆盖和明确空状态，显示影响范围 | 指定组重新跟随自动，其他组和自定义不变 |
| 添加或移除自定义标记 | 更新指定归属并追加事件 | AI 不参与 |
| 改自定义名称 | 修改定义显示修订并记录管理事件 | 关联收藏仍使用同一身份 |
| 查看标签或历史 | 只读 | 不产生采用、确认或训练信号 |

重新添加一个曾被排除的标签表示人工采用；选择恢复自动表示交回判断，两种操作不能混为一谈。

撤销追加补偿事件，恢复此前的人工状态，而不是简单取反当前显示值。此前若是跟随自动，撤销后跟随最新 AI；若 AI 已变化，页面说明当前结果与当时不同。此前若是人工采用或排除，恢复对应状态。

用于撤销的状态也包含组级自动屏蔽与单标签重新纳入自动的标记。撤销整组清空需要恢复清空前该组的完整人工状态，不能只把“空”标志改回去，或把旧有效标签全部写成人工采用。

替换是一次用户意图，两个底层动作必须一起成功或一起失败。一个批量操作可以包含多个动作，但当前操作与每个实际动作均有可追溯身份。

请求携带操作 ID 与预期人工修订。重试同一操作不会重复增加事件，异内容复用同一 ID 返回冲突。显式确认、撤销和全组操作还需要绑定用户实际读取的结果或前序事件，避免确认过期建议、覆盖另一端的新修改。

遇到并发修改，返回实际差异并保留草稿，允许用户重新应用自己的动作。不能用最后一次写入静默覆盖另一端。模型刷新同样不能覆盖正在编辑的内容。

## 九 历史记录和优化依据

### 记录范围

用户归属变更、AI 运行与决定、词表定义变更、自定义定义管理分别记录，不塞入一个含义不明的“来源”字段。当前有效结果可重建，不要求每次浏览都记录事件。

一次归属变更至少保留以下事实：

| 记录项 | 用途 |
| --- | --- |
| 事件 ID 和操作 ID | 区分用户动作，防重复，关联替换与撤销 |
| 收藏 ID 和标签身份 | 定位本条关系，避免改名后失联 |
| 动作和分组范围 | 区分采用、排除、确认、恢复、明确清空 |
| 操作者类型和可用的账户身份 | 区分人工、模型、迁移和词表管理 |
| 前后人工状态和有效归属 | 解释用户实际改变了什么，正确撤销 |
| 内容修订和标签定义版本 | 区分内容变化、词表变化与模型错误 |
| 词表发布版本和显示修订 | 解释当时可选项与名称，不用现名冒充旧界面 |
| 对应 AI 运行和决定引用 | 复现当时建议、策略与原始概率 |
| 前序或被撤销事件引用 | 解释替换、撤销与重复整理之间的因果 |
| 时间和可选原因 | 展示历史，辅助区分纠错与展示偏好 |

历史中只知道来源未知的旧记录继续标未知。不能把当前模型、当前定义或当前账户倒填成历史事实。事件只引用必要证据，不在每条日志里重复全文、提示词或凭据。

保存收藏原因、整理状态等动作仍可记录自己的事件，但不伪装成标签确认。事件记录应与实际写入成功一起提交，失败请求不生成成功变更历史。

### 保留期和删除

标签人工决定是当前有效结果的依据，不能被通用诊断日志清理影响。建议新增或扩展轻量、专用的标签变更事实，使其在收藏仍存在期间保留；详细诊断输出、无人引用的旧运行可以继续采用独立期限。

当前源码的通用 `curation_events` 默认会按 90 天清理，`curation_overrides` 仍作为人工真相保留。因此不能仅复用这个通用事件表就宣称具备长期完整变更记录。实施时需要调整保留策略或建立专用记录，并与已有清理流程明确分工。

需要作为评测样本的历史来源，必须建立合法的证据引用并纳入保留保护，否则只保存模型运行 ID 也不能保证材料可重现。来源已清理的旧事件标记证据不可用，不用当前正文替代旧版本。

删除收藏时清除该收藏的归属、变更和可关联的反馈样本，遵循现有删除合同。标签定义和其他收藏不受影响。历史不可覆盖不等于无限保留，更不意味着删除收藏后仍保留可识别副本。

### 如何使用反馈

操作首先表达用户在本条收藏上的决定，其次才可能构成分类质量信号。默认遵循以下规则。

| 反馈 | 能支持的结论 | 不能直接推断 |
| --- | --- | --- |
| 用户明确确认一个标签 | 此用户在当时内容和定义下认可该归属 | 整条所有标签正确、其他候选错误 |
| 用户添加一个系统标签 | 存在明确的人工正向归属 | 整个维度已经完整标注 |
| 用户移除标签且选填错分原因 | 可形成该标签的负向纠错候选 | 原因一定是模型，而非来源或定义问题 |
| 用户移除但未给原因 | 用户不希望保留该归属 | 必然是语义错分或完整负样本 |
| 用户将 A 替换为 B | A 和 B 之间存在有价值的纠正关系 | A 与 B 必然同义，或应全库合并 |
| 用户添加自定义标记 | 某种个人组织需求存在 | 应直接升级为系统主题 |
| 用户没有编辑 | 人工态度未知 | AI 判断正确 |
| 用户只看详情或保存备注 | 阅读或备注行为 | 标签已确认 |

初版只汇总建议，不根据单次操作自动改词表、改阈值或执行全库重评。重点观察明确错分、人工补充、重复替换、近义自定义需求和真实筛选行为。

只有在内容版本、定义版本和人工动作可解释时，才生成逐标签的部分参考答案。未确认的其他标签保持未知；小样本不当作整库准确率。对同一微信工具、同一项目或近似内容建立分组，避免把重复收藏拆进开发和验证集合。

优化分别检查来源是否缺失、词表边界是否含混、模型判断是否错误、策略阈值是否不适合。修改定义需要重新判断；只调整阈值可复用适用的原始判断。保存历史的目的，是让这些原因可以区分，而不是让系统从任何点击自动“学习”。

## 十 面向 Jev 的判断设计

### 选择合适的判断方式

主题和资源类型可以同时成立，因此每个候选分别判断是否适用，不用一个单选问题强迫它们竞争。对第一版 12 个主题和 6 个资源类型，核心标签判断共 18 个独立问题；兼容旧字段和次要属性所需的问题另行计入预算。

Noul 用于是否符合某标签；Choice 用于确实需要选一个结果的场景；Score 用于有明确等级描述的程度判断。255 是单个 Choice 问题的选项上限，不能据此把整个标签体系限制为或扩充到 255 项。[Noul 文档](https://docs.typesafe.ai/primitives/noul)、[Choice 文档](https://docs.typesafe.ai/primitives/choice)、[Score 文档](https://docs.typesafe.ai/primitives/score)。

不新增强制的“主要标签”问题。列表优先级由确定的展示规则处理；只有用户确实需要唯一主分类时，才单独设计 Choice，而不是消耗单选概率分布来充当多标签归属。

### 问题和证据

每个问题包含独立的完整含义、正反例和必要排除条件。例如判断图像生成，应识别内容是否实质介绍生图或编辑任务；判断 Skill，应识别明确的可复用技能资源。不能把“图像生成且为 Skill”捆绑成一个问题，否则无法解释是哪部分不成立。

复用已经存档、绑定版本的原文和结构化上下文，不因为分类重新搜索来源。原帖、作者续帖、引用、外链和第三方评论保持角色区分；只有评论提到某主题，不能直接替原帖赋该主题。客观分类不读取用户的待试、立场、自定义标记或收藏原因作为内容事实。

Jev 当前接受文本输入；图片、音视频需要已有可信的文本或结构化描述才能参与判断。只有图片 URL 而没有内容描述时，不宣称模型已理解图片内容。[模型输入说明](https://docs.typesafe.ai/models)。

### 决策和运行

独立问题可以使用同一份证据一起提交，实际请求仍受项目已有的字符、字节、token、时间和持久调用预算约束。增加问题会增加输入，不能把并行评估理解为免费；也不能预先承诺固定耗时或准确率。

原始判断与阈值策略分开保存。低概率、中间概率和协议失败分别处理；一个不确定候选不会清空其他可靠标签。阈值须根据真实收藏和误标、漏标代价验证，本文不指定未经校准的数值。

分类写入必须检查来源、问题、词表、策略和目标 generation 的适用身份。旧结果不能覆盖新来源。新词表定义只能通过受控目标切换生效，不因本地配置文件变化自动启用。

初版沿用现有持久预算和队列，不新增自动回填或付费循环。真实模型评测和历史重评的调用范围在实施阶段另行明确。

## 十一 数据对象和接口职责

下表是逻辑对象，并不要求每项都新建一张表。应尽量复用现有 Worker 和 Go 的结构，避免双写两套人工真相。

| 对象 | 主要事实 | 现有基础或新增要求 |
| --- | --- | --- |
| 标签定义 | 稳定身份、分组、名称、别名、版本、状态 | 复用系统 taxonomy 配置，新增自定义定义与统一引用 |
| AI 运行与决定 | 输入、问题、模型、原始判断、策略和建议 | 复用 classification_runs 和 classification_decisions |
| 人工归属决定 | 按收藏和标签的采用、排除、恢复及组级空状态 | 复用 curation_overrides，扩展资源类型，保持单一真相 |
| 标签变更事实 | 前后状态、操作者、因果和适用版本 | 扩充事件事实与保留策略，不能只依赖通用短期日志 |
| 当前有效结果 | 用于查询和展示的合并结果 | 复用确定性 resolve 和当前查询投影，明确自定义隔离 |

接口应覆盖读取词表、读取当前标签、读取 AI 建议和排除项、提交增量动作、读取分页历史以及管理自定义定义。接口名称在实现时与既有路由统一，不在本文假设新的端点已经存在。

按标签提交的概念载荷示例如下，它是拟议合同，不是当前 API 的调用示例。

```json
{
  "operation_key": "unique-client-operation",
  "expected_revision": 12,
  "operations": [
    {
      "action": "replace",
      "from_tag_ref": "system/topics/ai_coding",
      "to_tag_ref": "system/topics/image_creation"
    }
  ]
}
```

服务端校验标签身份、分组、版本、所有者、是否可新选和预期修订，将动作、操作回执、有效结果和缓存失效原子保存。响应返回实际有效结果和新修订，不依赖客户端整包覆盖标签数组。API 需要区分无改动、明确确认、冲突和重复操作。

资源类型是新的独立维度，不能借用 carrier 或改变 content_functions 原有 ID 的含义来偷渡。现有 source、实体、个人原因、整理状态、来源结构和旧用途继续使用原合同，界面退居次要位置不等于删除其数据。

## 十二 当前代码基础和需要补齐的部分

以下结论来自当前工作区源码核查，不代表生产部署状态或全链验收。

| 已有基础 | 可复用内容 | 本方案的补齐要求 |
| --- | --- | --- |
| 版本化词表与定义 | 稳定词条、别名、正反例、spec 身份 | 新定制主题、独立资源类型、自定义命名空间 |
| 分类运行与策略决定 | 原始判断、模型、内容与问题绑定、可重放决定 | 给新维度保持相同身份和预算合同 |
| 逐标签人工覆盖 | accept、reject、reset、明确空、幂等与修订检查 | 默认编辑器统一走增量动作，替换有操作级因果 |
| 有效结果解析 | 人工优先，排除不随重放复活 | 逐标签来源展示，不以整条 reviewed 布尔值冒充全部确认 |
| 事件和清理流程 | 通用事件、人工真相、受保护运行 | 明确长期标签事实、诊断期限和评测证据保留 |
| 多维查询和兼容 | 当前筛选、分页、计数、旧客户端协商 | 新资源、自定义字段的读写、筛选、导出和端侧能力声明 |

现有整组选项保存桥接 `persistSelectionOverrides` 可能把 wanted 中的所有标签追加为人工采用，并在集合不同于自动结果时写入整维明确空。该行为可服务旧客户端的整体替换语义，但不能作为新编辑器移除一个标签的默认提交方式。

## 十三 迁移和实施顺序

### 第一阶段 冻结标签定义和编辑语义

确认第一版 12 个主题、6 个资源类型及边界，检查别名冲突。以真实收藏建立代表性样本，覆盖重复项目、跨主题资源、只有链接、缺正文和无匹配等情况。先明确增量采用、排除、确认、撤销、明确空和恢复的合同，再调整 UI。

保留旧词表身份和人工结果。LLM、工程不能无证据拆成图像生成、写作或 AI 编程；旧工具也不能直接变成 Skill、软件或模型。显示名称相近不代表定义等价。

### 第二阶段 补齐身份 历史和查询合同

扩展资源类型与自定义标记能力，接入现有人工真相和原子写入。完善逐标签来源、操作因果、历史版本、保留与删除。旧未知来源继续标未知，已被清理的历史不伪造补全。

资源类型和自定义筛选必须由服务端处理并返回实际能力。旧客户端不能编辑无法表达的新字段；安全兼容时只更新原字段，有歧义时保留数据并明确提示。新响应不得无协商破坏旧严格解码客户端。

### 第三阶段 完成默认体验并小批验证

列表和详情展示主题、资源，接入增量编辑、撤销、恢复自动和真实计数；检查 Web 与 Android 的保存、缓存、并发和筛选一致性。

先通过离线合同与浏览器验证，再在明确的调用预算内执行有限真实分类评测。新定义和策略经受控 generation 切换后才用于新收藏。不能把发布词表等同于自动全库重评。

### 第四阶段 按需改善历史与反馈

历史旧标签仍能阅读和检索。需要重新分类的收藏使用已存档来源按明确范围入队，保存新 AI 建议，不覆盖旧人工决定。反馈页仅提出定义、合并或阈值建议，不自动激活语义变化。

回退 UI 或关闭新能力不删除新标签、历史和人工状态。回退到旧分类目标时，新维度可保持只读，不能为了兼容压平、截断或清空无法表达的数据。

## 十四 验收场景

| 场景 | 必须结果 |
| --- | --- |
| 从不创建自定义标记 | 能完成收藏、自动分类、浏览、全文搜索、主题与资源筛选、导出 |
| 写真 Skill 自动分类 | 图像生成和 Skill 可同时出现，不因使用 Codex 泛打 AI编程 |
| 普通云端模型能力介绍 | 可判断对应主题，不凭模型名就赋模型资源 |
| 多种资源的合集 | 保留实际 Skill、软件等类型，不被合集覆盖 |
| 没有合适主题 | 收藏仍在全库，可搜索，不强行匹配生活或LLM |
| 只有图片 URL 或缺正文 | 不冒充理解图片，缺证据与有效空分开 |
| 删除 AI 的一个标签 | 只排除该标签，不确认其余标签，不冻结该组 |
| 再分类出现一个新标签 | 未触摸的新标签可生效，已排除项不复活 |
| 人工添加系统标签 | 保持系统身份，显示人工添加，模型不能移除 |
| 确认一个标签 | 即使显示不变也有确认事件，其他标签仍未确认 |
| 只修改 why 或整理状态 | 不产生标签确认 |
| 将 A 替换为 B | 两动作原子完成，历史显示一次替换，失败不半成功 |
| 明确这一组都不适用 | 保存组级空决定，阻止该组自动新增，其他组不受影响 |
| 单标签恢复自动 | 只移除该标签人工覆盖，使用最新 AI 建议 |
| 手动清空后只恢复一个标签 | 仅该项重新跟随 AI，其他项继续屏蔽；界面说明仍关闭本组自动新增 |
| 撤销删除且 AI 已变化 | 恢复此前人工状态，说明结果可能随最新 AI 不同 |
| 连续点击或网络重试 | 同一操作只提交一次有效变更和回执 |
| 另一端同时编辑 | 保留草稿并返回差异，不静默覆盖 |
| 创建同名自定义标记 | 引导使用已有系统项，已有历史冲突有明确消歧 |
| 修改标签显示名 | 身份不变、历史可解释，不触发新的模型判断 |
| 两个维度使用相同词条 ID | 改名、历史与筛选均按完整身份隔离，不互相覆盖 |
| 标签含义或来源变更 | 历史保留原版本，人工不被伪装成对新含义的确认 |
| 合并两项但人工态度冲突 | 保留原决定，不替用户猜测新目标归属 |
| 通用历史清理运行 | 当前人工决定和承诺保留的标签事实不丢失 |
| 删除收藏 | 本条归属、关联历史和反馈样本按删除合同清除，其他收藏不受影响 |
| 导出有折叠标签的收藏 | 导出全部有效值和来源，不改变确认状态，不调用模型 |
| 手机与键盘操作 | 添加、移除、撤销均可完成，长标签不遮挡操作，状态变化可感知 |

## 十五 实施范围和交付边界

第一版实施范围包括主题与资源分类、可选手动自定义标记、逐标签编辑、身份与变更事实、筛选和导出、兼容迁移及必要的反馈汇总。

暂不建立深层分类树、自定义自动归属规则、自动发明标签、强制个人用途、按点击自动改词表、未经范围确认的付费回填或模型重要性评分。这些能力只有在实际使用证明有价值时才另行设计。

本次交付的是可用于产品与工程评审的设计文档。源码、生产词表、分类目标、数据库和线上历史均未随本文修改。下一步实施应围绕上述验收场景逐项落实，不能以新增字段或模型返回成功代替实际用户体验验证。
