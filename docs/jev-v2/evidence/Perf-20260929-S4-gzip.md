# S4: dashboard response compression (2026-09-29)

The dashboard now precompresses embedded HTML, CSS, JavaScript and SVG at startup. A browser that accepts gzip receives the compressed variant. Static assets have separate strong ETags for plain and gzip bytes, plus `Vary: Accept-Encoding`; a matching request still receives a bodiless 304. The application shell keeps its CSP and `no-store` policy. The private image proxy is unchanged, including its exact upstream `Content-Length` copy.

For API JSON and text responses, gzip starts only after 4 KiB has been written. The compressor is reused, and no more than eight responses compress at once; excess concurrent responses continue as plain bytes without waiting. Short replies and error responses stay plain. This bounds compressor concurrency and avoids spending CPU on tiny responses.

`make verify` passed, including race tests, lint, the 488 frontend checks and the Go build. Focused tests check decompression with Go's standard library, gzip negotiation including `q=0`, distinct variant ETags and 304, HTML security headers, large JSON, full compression capacity and unchanged private image bytes.

The local handler benchmark used an AMD Ryzen 9 7900X and 50 synthetic bookmarks with distinct per-item content. Three runs of `go test ./internal/dashboard -run '^$' -bench '^BenchmarkDashboard(JSON|Static)Transfer$' -benchmem -benchtime=500ms -count=3` measured:

| Response | Plain wire bytes / time | Gzip wire bytes / time |
| --- | ---: | ---: |
| 50-item JSON | 28,378 B / 31–33 µs | 2,807 B / 58–59 µs |
| Embedded CSS | 52,066 B / 8.7–10.1 µs | 10,341 B / 3.0–3.2 µs |

The first standard-library gzip prototype took 72–74 µs for the same varied JSON and allocated about 48 KiB per request after pooling. The selected `klauspost/compress` stateless writer took 58–59 µs and about 44 KiB, with a slightly smaller response. The CSS variant is faster to serve because it is compressed only once at startup. These are handler-level synthetic measurements without a network, Worker/D1 latency or background source processing. They establish transfer savings and the CPU tradeoff; #20's mixed-load p95/p99 and memory-stability targets still require the full baseline workload before deployment.
