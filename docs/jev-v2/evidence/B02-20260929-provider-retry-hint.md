# B02-T07 局部交付：供应商退避提示进入持久分类任务

日期：2026-09-29。[TypeSafe HTTP API](https://docs.typesafe.ai/api.md)列出 429 限流和 529 过载，要求使用指数退避；[TypeSafe SDK 重试文档](https://docs.typesafe.ai/sdk/python/api/retries.md)支持 `Retry-After` 和 `retry-after-ms`。此前 Go 把这些状态归类为暂时故障，但丢弃了响应头；Worker 仅按任务尝试次数设置固定重试时间。进程内分类暂停从 30 秒开始，可能早于供应商给出的提示结束。

## 修复与边界

- TypeSafe 响应头按毫秒扩展、标准秒数和 HTTP 日期解析；无效值忽略，超过 10 分钟的提示截到 10 分钟。只传递时长，不记录原始响应头或供应商可能回显的正文。
- Go 的进程内分类暂停至少持续到提示时长；当前分类任务的失败报告附有 `retry_after_ms`。Worker 在原有任务退避上增加 0–20% 抖动，持久 `next_retry_at` 取原退避与有界供应商提示的较晚值；每任务最多保留既有 2 小时退避上限。无提示和旧客户端仍可使用原接口。
- Worker 在改动租约前拒绝负数、字符串或非整数提示。已知 429/529 响应不会在同一次 Go 调用里自动再发付费 POST。供应商结果未知时继续由既有持久账本阻断盲目重发；本次没有放宽预算或重置尝试次数。

## 验收

- Go 单测覆盖两种响应头、HTTP 日期、优先级、畸形/负数/过大值，以及 TypeSafe 529 夹具到分类失败请求体的传递。Worker 本地 D1 测试覆盖无提示抖动、8 分钟提示、超长提示截到 10 分钟、无效提示不改租约。
- 真实本地 Go→Worker/D1 用一个本地 TypeSafe 529 夹具验证：模型调用恰好一次，8 分钟提示保存在任务 `next_retry_at`；新建 Go 处理器后，同一任务仍不能提前领取或再调用模型。`make verify`、`make test-ablation`、Worker 全量测试、类型检查和 dry-run 的精确结果见本次 issue 交付记录。

## 仍待完成

这只持久化**当前任务**的重试时间；其他分类任务的组件暂停仍在 Go 进程内。多实例或重启后，另一个待分类任务仍可能在供应商冷却期调用 TypeSafe。B02-T07 需要 Worker 侧跨进程组件门闩、独占半开探测、source/reading/classification 分开的健康状态，以及持续负载下的预算和恢复验收。#16 的旧新二进制、生产迁移/回滚、真实付费对账和观察期也未由本地夹具证明。原 B02-T07 复选框保持未勾选；未部署、发起真实付费调用或执行远端迁移。
