### Worker 真正事务边界

`worker/test/completion-atomicity.test.ts` 使用 workerd 的真实本地 D1。测试只包装 DB.batch 的调度，在 endpoint 最后预检查之后、真实 batch 之前改变 target、content revision 或 lease；全部 SQL 仍在真实 D1 执行，不把 SQLite helper 结果称作产品通过。

12 项回归覆盖 legacy/v2：三种失效窗口、不同 operation 并发、SQL 失败回滚与恢复、相同 operation 并发和丢响应重试。检查 HTTP、job 状态、成功 run/decision/operation、分类值、selection 以及后续领取。

- 修复前：target/content 四个用例得到 HTTP 冲突但 job=completed，见 [失败日志](logs/20260922-runtime/r3-01-before.log)。lease 与正常幂等控制用例原本通过。
- 深入回归另发现 legacy 在另一 operation 抢先完成后生成错误成功凭据；现将凭据和最终 job 转换一并置于同一守卫下。SQL 失败按实际 Worker fetch 抛错处理，并核实事务回滚后可重试。
- 最终：Worker 129/129，包括新增 12 项；types/typecheck 与 deploy:dry-run 通过，见 [最终日志](logs/20260922-runtime/worker-r3-final.log)。

### 真正本地跨服务联调

单独执行 `bash tests/local-integration/run.sh`：每个用例启动独立 wrangler dev、真实 Worker/D1/R2，使用实际 Go client/classifier；外部 TypeSafe 边界为受控契约 fixture，不收费。

三个用例均通过：FullLifecycle、VersionCompetition、DisplayRenameKeepsSemantics。[最终日志](logs/20260922-runtime/local-integration-r3-final.log)。FullLifecycle 在真实 D1 成功提交后仅丢弃第一次 HTTP 响应，断言 2 次相同提交、1 次模型请求、1 个持久 run；未用 generic completed 代替操作确认。

第一轮并发执行 Go race、Worker 全套与本地多实例联调时，Worker 一个既有测试触发 5 秒超时（[原日志](logs/20260922-runtime/worker-r3-gates.log)）。停止其他重任务后，以原 npm test 配置运行最终代码全部通过；未放宽 timeout 或删断言。本机资源竞争是对现象的解释，后续实际 CI 仍须单独核对。
