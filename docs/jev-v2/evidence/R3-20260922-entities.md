## Behavior

The processor retains the verified immutable snapshot payload after the R3-02 identity/hash checks. Extensions consume its actual block IDs, text, roles and order. An unbound legacy job cannot manufacture an entity result from plain-text fallback. The entity payload identifies the actual snapshot ID, content hash and ContentRevision, independently of source InputRevision and queue Revision. Its operation key also identifies the classification attempt.

Migration 0019 adds durable entity-operation receipts and a snapshot ID to independent entity state. One D1 batch conditionally records a receipt only for the current matching snapshot, applies it once, and marks it applied. A source change after preflight produces 409 and no receipt/state. Exact successful operation replay remains valid after subsequent results or content changes; changed payload/link with the same key conflicts. Replaying an old success cannot replace a newer result. Failure/not_run preserve both completed-nonempty and completed-empty values at the same full snapshot identity; failures for a genuinely new current revision may be recorded.

Current automatic entities require matching revision/hash/snapshot. Historical rows remain archived, and unbound migration-era states are not certified as current. Human overrides still apply to the current automatic baseline; reset does not retain a historical human-origin badge. The SQL effective_entity_terms view derives the same per-term accept/reject/reset/set-empty semantics directly from current state and the action log. Search uses it rather than a stale projection cache. Existing legacy full-text metadata remains searchable until an independent entity state or entity correction exists; this compatibility fallback is historical text, not a newly verified entity run.

Entity writes rebuild the derived display projection. The reading header and entity panel share current effective results, and both the actual client download button and server Markdown export read current entities instead of old classification.entities. The integration harnesses now launch each local Worker in its own process group and stop that group, preventing child processes from accumulating between scenarios.
