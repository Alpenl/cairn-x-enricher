# 消融实验结论

> 本文记录此前的真实模型质量实验。本轮另外执行了离线架构消融、浏览器性能对照和 Android/Worker 同步验证，见 [简化与同步报告](simplification-and-sync.md)。当前代码已直接执行 Go 富化流程，本文关于 Eino 包装的故障描述作为历史记录保留。

本文件是 `experiments/` 消融实验的结论。数据来自对真实模型端点（`https://tk.alpenl.com/v1`，
`grok-4.6`）的 35 次实际调用，覆盖 9 个消融变体 × 4 条已验证的真实 X 帖子。
逐条原始输出、评分与失败原因见 [ablation-report.md](results/ablation-report.md) 与
[ablation.json](results/ablation.json)。方法、评分定义与复现步骤见 [experiments/README.md](../experiments/README.md)。

## 结论速览

| 结论 | 证据 |
| --- | --- |
| **strict JSON Schema 是硬性前提**，移除后全部样本不可解析 | 通过率 0%，3/3 返回 `unknown field "title"` 等自由文本 |
| **`x_search` 不可替代**，移除后模型改写记忆而非读取原帖 | 原文保真 0.09，50% 结构拒绝，质量 0.000 |
| **线程评论读取不改变检索结果，却是可靠性保险** | 真实收藏 14/17 原文**逐字节相同**（中位比 1.00×）；完整消融中 Δ质量 +0.000 |
| **搜索证据门禁限制的是能否编造** | 真实语料 Δ质量 +0.007，说明门禁本身几乎不花钱；但 `no_x_search` 0% 通过证明没有证据就无法区分编造 |
| **中文标题校验器是承重的质量约束** | 真实语料移除后 Δ质量 **−0.199**，通过率降至 80%（两次均为标题超长 36/33 字符） |
| **译文与分类是真实的质量增量** | 移除后质量 −0.100 / −0.050 |
| **已有原文时，`source_only` 是最优路径** | 真实语料质量 **1.000**、保真 1.00、通过率 100%，token 比 FULL 低 33% |

## 一、按“承重程度”分层的设计

消融结果把流水线的设计清晰地分成三层，而不是一条连续曲线。

### 第一层：硬性前提（移除即完全失效）

**strict JSON Schema**（`no_strict_schema`，质量 0.000）

移除结构化约束后，模型返回的是带中文字段名的散文，而不是 JSON 对象：

```text
标题：卡帕西认为分词器是大语言模型的一个瑕疵
原文语言标识：en
完整原文：Yes, thinking about it more, the tokenizer is a bit of a wart in LLMs.
```

3 个成功返回全部无法解码。这条设计不是“提高稳定性”，而是**协议本身**：
`decodeStrictJSON` 使用 `DisallowUnknownFields`，没有 schema 时模型会自创字段名
（`title`、`标题`），直接触发拒绝。

**`x_search` 服务端工具**（`no_x_search`，质量 0.000，保真 0.09）

移除工具后，模型不是“读取失败”，而是**流畅地编造**内容。以 sample 304 为例，
真实帖子是 DeepSeek V3 竞技场排名，模型输出的却是另一段同样通顺的技术评论：

| | 原文 | 保真 |
| --- | --- | --- |
| 真实帖子 | `DeepSeek V3 的LLM竞技场评分出来了 目前排第七…` | — |
| `no_x_search` 生成 | 编造的英文技术描述 | 0.00–0.22 |

这是最危险的失败模式：标题、译文、摘要全部自洽且格式合规，**8 项结构校验无一能发现**。
它直接证明了“搜索证据门禁”必要性——它是唯一能区分“检索到”和“编造得像”的信号。

### 第二层：真实的质量增量

| 变体 | Δ质量 | 说明 |
| --- | --- | --- |
| `no_translation` | −0.100 | 译文是产品的核心价值，移除后字段产出率降到 0.88 |
| `no_classification` | −0.050 | 封闭词表分类贡献可测，成本约 856 token |

两者都保持 100% 通过率，说明它们是**增量价值**而非前提条件：
没有它们结果依然可用，只是不完整。这与第一层的“完全失效”形成清晰分界。

`source_only`（质量 0.900，保真 1.00，token −30%）在**已有可信原文**时表现优异。
它的唯一质量损失来自 sample 301：该帖很长，模型对超长原文做了压缩。
这说明恢复路径适合短帖，长帖仍需注意截断。

### 第三层：本语料上无差异（需要更大样本才能定论）

| 变体 | Δ质量 | 关键观察 |
| --- | --- | --- |
| `no_thread_context` | +0.000 | 原文**逐字节相同**，但 token 12563 → 11103（−11%） |
| `no_search_evidence_gate` | +0.000 | 变体与 FULL 请求相同，仅放松验收，本轮无触发 |
| `unconstrained_title` | +0.000 | 4/4 输出仍为 22–28 字合规中文标题 |

**`no_thread_context` 是最值得跟进的发现，并已在真实数据上复测（见第三节）。**
第一轮它是**输出完全相同**（原文长度 3128/160/333/128 与 FULL 一致），却少了 1460 token：

```text
sample  FULL        no_thread_context
301     3128 chars  3128 chars   (逐字节相同)
302      160 chars   160 chars
303      333 chars   333 chars
304      128 chars   128 chars
```

即：对这 4 条帖子，评论检索**没有改变任何被写回的内容**。可能的解释是这些帖子
本身信息自足。是否在生产中保留线程读取，取决于真实收藏中“正文在评论里”的比例——
本实验无法回答这一点，但给出了明确的测量方法。

`unconstrained_title` 的零差异**已排除评分器缺陷**：手工核对显示 4 条输出全部
满足 8–32 字且含中文。这说明模型默认行为已经满足约束，校验器在此语料上属于
**防御性安全网**，其价值体现在模型漂移或提示词被改动时，而非当前质量提升。

## 三、真实收藏上的线程读取复测

第一轮消融只有 4 条语料，得出“线程读取输出逐字节相同却多花 ~11% token”的初步结论。
本节用**真实收藏库**（从 Worker 拉取 17 条已完成、含原文的 X 书签，按长度均匀取样）复测，
结论方向一致但幅度更大，并揭示了一个第一轮无法看到的细节：线程路径在少数帖子上是**唯一能成功**的路径。

模型 `grok-4.6`，每个书签分别用“读线程”与“只读原帖”两种提示词各跑一次。

### 这一节如何改变结论

真实数据把第一轮的结论从“线程读取没用”修正为更精确的判断：

| 观察 | 含义 |
| --- | --- |
| 14/17 原文逐字节相同，长度中位比 **1.00×** | 线程内容**没有**进入被写回的正文 |
| 0/17 出现 post-only 更长 | 线程读取不会损害检索 |
| 差异的 3 例全部是线程变体更可靠（post-only 失败 3 次 vs 线程失败 1 次） | 线程路径是**可靠性保险**，不是质量来源 |
| 平均 **+2781 token（+24.8%）** | 保险的保费不低 |
| 对照实验：同一提示词跑 3 次，原文完全一致但标题三次全不同 | “标题变化”是采样随机性，**不能**作为评论价值的证据 |

因此线程读取的正确定位是：**为少数“正文取不全”的帖子兜底**。
是否保留取决于这类帖子的真实比例。本实验给出的是测量方法与该比例的初步估计
（3/17 ≈ 18% 出现单边失败，其中线程侧胜出）。

**`unconstrained_title` 的修正是本轮最重要的发现。** 冻结语料上 4 条样本的标题
恰好都在 8–32 字内，所以移除校验器看不出差别，我据此写了"它在本语料上是安全网而非
质量驱动"。真实语料上它立刻暴露：两次失败都是**标题超长**（36 和 33 字符），
模型默认会生成更长的标题。

```
sample 11: 36 字符  "谷歌Gemini Omni 1.1 Flash视频模型评测：强却关注度低"
sample 23: 33 字符  "开源微信个人情报库 wechat-intelligence-hub"
```

**教训：4 条样本不足以判定"某设计无差异"。** "零效应"结论必须用足够大的语料验证，
否则会把承重的设计误判为可移除。这正是第 2 节那条"建议复测"存在的原因 —— 现在复测完成了。

## 五、方法论教训（重要）

实验过程中出现并修正了一个**会给项目扣上假缺陷的**错误，记录在此以避免重犯：

第一版语料把 post ID `1991910395720925418` 标为 `xai` 的帖子，但该 ID 实际属于
`@karpathy`（Animals vs Ghosts）。模型忠实返回了 Karpathy 的正文，却被判为
“身份错误”——一个**完全由错误语料伪造出来的缺陷**。

因此 `experiments/verifyurls` 现在是计分前的强制门禁：它用端点解析每个 sample URL
的真实作者与链接，并与 URL 中声称的作者比对，不一致即中止。当前语料
（`karpathy` / `yoko_materialDX` / `OpenAI` / `op7418`）已全部通过校验；
真实收藏语料由 `experiments/harvest` 从 Worker 直接拉取，同样只保留已存在原文的记录。

同样的教训体现在评分器上：最初的 `qualityScore` 不惩罚低保真，
`no_x_search` 这个**编造内容**的变体拿到了 0.867 的高分。现在
`Grounded` 作为硬门禁——与已知原文的相似度低于 0.45 直接判 0 分。
若没有这一步，本报告会得出“去掉 `x_search` 便宜又不掉质量”的**完全相反**的错误结论。

## 六、可执行的建议

1. **保留 strict JSON Schema 与 `x_search` 及其证据门禁。** 二者是硬性前提，
   任何“省钱”的移除都会让结果从“可用”变成“有害”。
2. **把线程读取当作可靠性保险，并据此决定去留。** 真实数据（第 3 节）显示它不提升
   正文质量（14/17 完全相同）却多花 ~25% token，但在少数帖子上是唯一能成功取到内容的路径。
   建议保留，并监控“post-only 失败而线程成功”的比例；若该比例长期极低再考虑切换。
3. **优先扩大 `source_only` 路径的适用范围。** 对已有 `original_text` 的失败记录，
   该路径质量 0.900 且便宜 30%；需为超长原文设置更明确的截断策略。
4. **不要移除中文标题校验器与分类词表。** 它们当前不提升质量（模型已合规），
   但成本极低，是模型漂移与提示词变更时的第一道防线。
5. **把“保真度”纳入生产校验。** 本实验最重要的发现是：结构校验无法识别编造。
   生产环境已有 `original_text` 时，可对重跑结果做相似度兜底，防止静默覆盖。

## 七、由本实验直接驱动的代码修改

前三节给出建议，本节记录**已经落地**的改动。三项全部来自真实数据，不是推测。

### 1. 降级链现在也响应“成功但不可用”的响应

`internal/enrich/responses.go`

原先只有**请求层失败**（可重试状态码）才降级到下一个提示词。如果某个提示词返回 `200`
却没带已完成的 X 搜索（真实数据里 bookmark 14 就是这样），客户端会直接返回这个必然被
校验拒绝的结果，**白白放弃一条本可由另一个提示词处理的收藏**。

现在降级条件扩展为三类：可重试的请求失败、响应无法解析为候选、以及**响应缺少搜索证据**。
不可重试的错误（`401/403` 等配置问题）仍然立即中止，避免把配置故障扩散到每条收藏。

端到端验证：对真实书签 14 调用真实端点，修复后 `search_verified=true` 并成功产出标题；
修复前该条会以校验失败告终。

安全网未变：`validateCandidate` 仍然拒绝任何缺少搜索证据的结果，现在是双层防护。

### 2. 失败消息把可诊断信息放在最前

`internal/enrich/workflow.go`、`internal/enrich/responses.go`

数据库里真实存过的失败记录：

```text
run Eino enrichment workflow: [NodeRunError] model API returned HTTP 5
```

70 个字符里 **45 个是框架前缀**（Eino 的 `[NodeRunError] ` 与本项目自己加的
`run Eino enrichment workflow: `），失败消息在 Worker 侧被截断后，状态码被腰斩成 `5`，
运维无法区分 500 / 502 / 503。

修改与效果：

| | 修改前 | 修改后 |
| --- | --- | --- |
| 存储内容 | `...model API returned HTTP 5`（截断） | `HTTP 502 upstream_error: Upstream service temporarily unavailable` |
| 状态码 | `5`（丢失） | `502`（完整） |
| 上游错误类型 | 未解析，直接丢弃 | `upstream_error`（保留） |
| 长度 | 70 字符（超限被截） | 65 字符（完整） |

两处改动：`Workflow.Enrich` 用 `errors.Unwrap` 剥掉 Eino 的框架包装；`readModelHTTPError`
额外解析并保留上游的 `type` 字段（原先只读 `message`，恰好丢掉了区分“上游抖动”与
“配额耗尽”的关键信息）。`errors.As` 仍能取回 `*ModelHTTPError`，重试判定不受影响。

### 3. 失败消息标注输入路径

`internal/processor/processor.go`

重试时如果已存有 `original_text`，服务会走恢复路径，绕开 `x_search`。
但**失败消息原先不区分两条路径**，运维无法回答"这条收藏的内容是真的取不到，
还是只是无法重排已有文本"。

| | 修复前 | 修复后 |
| --- | --- | --- |
| 搜索路径失败 | `model endpoint exploded` | `[search] model endpoint exploded` |
| 恢复路径失败 | `model endpoint exploded` | `[recovered_source] model endpoint exploded` |

区别很重要：只有**搜索路径失败**才意味着收藏内容仍然缺失；恢复路径失败说明只是
无法重排已存文本，而且**重跑同一个任务不会改善**（恢复路径不会重新抓取原帖）。
前缀而非后缀，因为存储的消息会被截断。完成日志同时记录 `path` 与
`original_text_bytes`，便于按路径统计。

### 4. 一次基于错误推理的改动（已撤销，记录以备后鉴）

我最初在 `internal/config/config.go` 加了一条硬性校验：`GROK_MAX_OUTPUT_TOKENS`
低于 4096 就拒绝启动，理由是"预算不足会让长帖静默截断"。

**这个前提经实测不成立，改动已撤销。** 长度扫描（`results/source-path-length-sweep.json`）：

| 原文长度 | 实际 output_tokens | 原文回吐 | 占请求的 8192 |
| --- | --- | --- | --- |
| 97 | 3,510 | 100% | 43% |
| 267 | 3,472 | 100% | 42% |
| 566 | 6,329 | 100% | 77% |
| 3,644 | 8,363 | 100% | **102%** |
| 3,922 | **12,557** | **100%** | **153%** |

另外对 3922 字符长帖改变预算：`1024 / 2048 / 4096` 全部返回 `upstream_error`，
但那与预算无关 —— 同一帖重试 8192 也失败，是端点抖动。

两点推翻了我的论证：

1. **`max_output_tokens` 不是硬上限**：8192 的预算下实际用了 12,557 tokens
   仍然完整返回，没有截断。
2. **低预算下的失败是 `upstream_error`，不是截断**：观察不到"静默返回残缺原文"
   这一现象。而且 8192 重试同样 `upstream_error`，说明那是端点抖动，
   与预算无关。

我当时是基于 3 个短样本的线性外推（斜率 ≈ 6 tokens/字符）预测"875 字符以上必然超限"，
并据此直接改了代码。**用外推代替实测，正是本报告第四节批评的那类错误。**
教训：配置级硬性拒绝必须有实测支撑，否则会把一个不存在的问题变成启动故障。

真正被实测支持的观察是：**长 prompt 的重请求更容易遇到 `upstream_error`**。
这不是配置能修的，但正是第 2 项修复（保留 `type` 字段）让它变得可识别 ——
运维现在能立刻看出是上游容量问题，而不是去查数据。

### 5. 实验自身的错误归因修正

`experiments/ablation/variants.go`

实验框架的 `validateOutcome` 缺少生产的**第一个**检查（搜索证据），导致
`no_x_search` 变体被报成 `original_text missing`，而真实原因是**没有搜索证据** ——
这正是本项目批评的那类误导性归因，出现在了我自己的实验代码里。

修正后 `no_x_search` 的拒绝原因直接指向“没有搜索证据”，让该消融的核心论点更有说服力。
**所有已发布的数值结论不变**（逐变体质量差 Δ 均为 0.000），仅归因更准确。

这一点在**真实收藏语料**上得到确认：`no_x_search` 的 10 次拒绝全部报
`model did not provide evidence of a completed X search`，无一例误报为字段缺失。
修复前这些会被报成 `original_text missing`，把运维引向错误的方向（去查数据问题，
而实际是模型根本没有检索）。

## 八、限制

- 冻结语料仅 4 条。足以判定“某设计是否承重”，不足以给出精确百分比；线程读取的结论
  已在 17 条真实收藏上复测（第三节），其余变体仍是 4 条语料的结果。
