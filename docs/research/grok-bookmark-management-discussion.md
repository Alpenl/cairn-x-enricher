我收藏了很多帖子，有微信公众号，更多的是X上的帖子，如何管理这些文件？我现在降他们都放在自己的数据库中，会使用LLM请求总结摘要，但是链接多了检索变得麻烦，也不好自动分类，和我讨论一下如何高效管理，不实用RAG，不建立复杂系统

Worked for 29s

核心判断先说清楚：不靠 RAG 的收藏库，几乎不可能靠“自动分类 + 事后搜索链接”规模化。 链接一多，检索变差不是工具不行，是模型选错了——你把“剪报堆”当成了“知识库”。

收藏 ≠ 知识。链接会失效，推文缺上下文，公众号会长、会改、会删。LLM 摘要能降低阅读成本，但不能替代你决定这条东西为什么值得留下。自动分类差，通常不是模型弱，而是标签体系无限膨胀、每条都想分到一个“正确抽屉”里。⁠Weixin.qq

下面按“尽量沿用你现有数据库、不加复杂系统”来谈。

1. 先换目标，再谈检索

两套完全不同的目标：

	档案馆	可用知识库
默认动作	能存就存	能不用就不用
检索对象	原始链接	摘要 + 你自己的一句话 + 主题笔记
分类	给每条找一个类	少量稳定标签，允许一条多标签
成功标准	东西都在	三分钟内能找到，或已经写进主题笔记

不建 RAG 的前提下，后一种才撑得住。前一种做到几千条就会崩。

实用原则就三条：

入库时多花 20 秒，比事后花 20 分钟翻强得多。
检索原始条目是备用手段；真正常用的是按主题合成的短笔记。
标签要少而稳，不要让 LLM 每次发明新类。
2. 你现在这套，卡在哪

你已经有：自己的库 + LLM 摘要。这比纯收藏夹强。剩下的两个痛点其实是同一件事：

检索对象错了：在搜“链接/标题”，而不是搜“你当初为什么存、以及一句话结论”。
分类目标错了：想自动把世界分成互斥文件夹。社交内容天然跨类（一条推文同时是工具、观点、人物、反例）。

所以不要追求“自动分对类”，改成：

入库时 LLM 只能从你固定的 20–40 个标签里选 2–4 个
另写一句 “我为什么存”（这句以后才是真正的检索钥匙）
原文/全文只做备份和偶尔精读

“为什么存”比摘要更重要。摘要是作者的话的压缩；“为什么存”是你的意图。三个月后你记得的是后者。

3. 轻量结构：一张表就够

不必上第二套系统。现有库加字段即可。建议字段压到这些：

固定元数据（尽量自动）

source：x / wechat / 其他
url、canonical_id（推文 ID / 公众号 msg id）
author、published_at、saved_at
type：insight / howto / tool / data / thread / longform / quote
status：inbox / kept / compiled / drop
原文文本或截取（推文全文；公众号可只存正文纯文本）

人机各写一次

summary：LLM，80–150 字
why：你或 LLM 起草、你改，一句话
tags：只许选自控词表，2–4 个
people / works：提到的人或项目，可选
score：1–3 就够，不要五星幻觉

检索层（仍然不是 RAG）

对 title + why + summary + 原文 做 全文检索（SQLite FTS5 足够）
筛选：source × tag × type × 时间 × status
不要做无限层级文件夹

这就是“分面检索”，不是语义检索。你记得“好像是某个人讲量化交易风控的长推”，用 author + tag:风控 + 关键词就能定位。记得“那句关于不要过早抽象的话”，搜 why 和摘要里的词。

自动分类失败时，几乎都是因为词表是开放的。改成封闭词表，LLM 只做“多标签选择”，准确率会立刻上去。每月花 10 分钟合并近义标签。

标签建议按维度拆，不要混成一棵树：

主题：llm 市场 设计 健康 …
形态：方法 案例 观点 数据 工具
用途：可引用 待试 反对意见 素材

一条推文可以同时是 llm + 方法 + 待试。互斥分类才会把系统逼死。

4. X 和公众号不要同一套待遇

这两种东西信息密度差一个数量级，入库策略应该不同。

X 帖子 / 串推

量大会脏。默认进 inbox，不直接当知识。
必须存：全文（链接会烂、串推会拆）、作者、发布时间、是否串推。
图片/截图里的字，值得存的才做识别；否则只留图链或本地文件路径。
真正有用的往往不是单条，而是“某作者在某周的一组观点”。更好的单位是 thread / 作者小专题，不是单条 bookmark。
每周从 inbox 里只 kept 一小部分，其余直接 drop。收藏时的兴奋感不可靠。

微信公众号

长、结构完整，更适合变成“一篇一卡”。
摘要可以稍长，并抽出 3 个要点 + 1 个可执行项。
正文尽量本地留一份纯文本，防链接失效、防改文。
不要每篇都精读。score=3 才进主题笔记。

采集入口可以继续用你现在的脚本；微信侧若只想减摩擦，用现成剪藏当中转也可以，但最终仍落回你自己的表，避免数据锁在别人家。ima、Cubox、Obsidian Clipper 都是入口，不是知识库本身。⁠Woshipm

5. 检索怎么变好：三层，而不是“搜索全部链接”

把库分成三层，维护成本很低：

L0 原始剪报

所有保存的帖子/文章。允许乱，但必须能 FTS。这层不追求整洁。

L1 卡片

status=kept 的条目。每张有 why + 摘要 + 标签。日常检索只搜这一层。

L2 主题笔记（这才是你真正会反复打开的东西）

每个你长期关心的主题一篇短文档，例如「评估 LLM 应用的标准」「个人投资检查清单」「好的产品文案句式」。

每周把新的 L1 往里面编译一句到三段，并链回原条目 ID。

以后你不是在 3000 条链接里找，而是打开 20–40 篇主题笔记。

这就是不建 RAG 时最划算的“检索预计算”。Karpathy 那种 raw / wiki 分层也是同一思路，只是你不必上 Obsidian 全家桶，一篇 Markdown 或库里一张 notes 表就行。⁠Cloud.tencent

查询习惯也要改：

“我记得有个东西” → 先搜 L2，再 L1，最后才 L0
“某作者最近说了啥” → author + 时间
“我想写某主题” → 打开对应主题笔记，而不是 keyword 扫库

LLM 的用法也从“每次对全库提问”改成：

入库时：摘要、选标签、起草 why
每周：把本周 kept 列表塞给模型，更新 3–5 篇主题笔记
偶尔：对单篇主题笔记 + 相关 10 条卡片提问
这不是 RAG，是你自己把上下文挑好再喂。
6. 自动分类为什么总让人失望，以及最小可用替代

LLM 开放分类会出三种垃圾：近义标签（AI/人工智能/大模型）、一次性标签（某篇文章里的专有名词）、错误抽屉（一条工具贴被标成哲学）。

最小规则：

词表写死在配置文件里，模型禁止创造新标签。
拿不准就标 untagged，进每周清理，不要硬分。
用 type（形态）代替一部分主题分类。形态比主题稳。
score 只用于决定去留，不用于排序审美。
分类的单位可以是“这周的 30 条”，不是“这一条”。批量打标比逐条准，因为有对照。

人的参与只留一个动作：改 why 或改标签，二选一，不超过 20 秒。 两样都不想改，说明不该 kept。

7. 每周 30 分钟就够，别做日常管理员

一套能长期跑的节奏：

每天（可选，2 分钟）

看到就丢进库，允许只存链接+原文，状态 inbox。不要当天整理完。

每周一次

看 inbox：删掉一半以上（drop）。
留下的补 why / 标签 / score。
把 score=3 的编译进主题笔记。
主题笔记里过时的句子直接改，不要留历史包袱。

每月一次

合并标签、看哪些主题笔记从未打开（主题可能是假需求）、物理删除确定无用的原文。

这比任何自动分类器都有效，因为知识库的熵是靠删除和编译降下来的，不是靠打标。

8. 明确不要做什么

在你给的约束下，这些性价比很差：

向量库 / RAG / Agent 自动巡库
知识图谱、自动关联可视化
为每条推文生成长文解读
精细文件夹树
想把微信、X、论文、聊天记录塞进同一套“万能本体”

链接腐烂、X 媒体、微信反爬，都当备份问题处理：能抓到正文就存文本；抓不到就接受“这条以后可能打不开”，不要为此上爬虫集群。

如果你愿意，下一步可以只做一件很小的事：按你真实会问的 10 个查找场景反推字段。例如：

“某条关于某某 API 坑的推”
“我存过的、能直接当 checklist 的文章”
“某作者我标过 keep 的全部串推”
“上周想试但还没试的工具”

你回我三样就行：大概量级（X / 公众号各多少）、你现在数据库是什么（SQLite？）、你最常发生的 3 个“明明存过却找不到”的场景。我可以按这三样帮你压一版更具体的字段和标签词表，仍然不加系统。

如何做到标签要少而稳，不要让 LLM 每次发明新类？

Worked for 17s

关键不是把提示词写得更严厉，而是不给模型创造标签的权力。模型只做“多选题”，程序做“门卫”。

1. 先定词表，再让模型选

标签稳定，靠的是三样东西叠在一起：

封闭词表：合法标签写在配置里，不在对话里现场生成
输出校验：返回值不在词表里就丢掉或映射，绝不入库
别名表：把模型爱发明的近义词收编成旧标签，而不是开新类

词表本身要小。个人库通常 25–40 个主题标签就够，再加几个形态标签。超过 60 个，人记不住，模型更会乱造。

不要做一棵很深的分类树。树会逼你为每个叶子发明名字。改成 两三个独立维度，组合用筛选完成，不靠新标签。

例如只维护两列：

维度	作用	数量
topics	这是关于什么	20–30 个，多选 1–3
form	这是什么形态	6–8 个，单选
use	我为什么留它	4–5 个，单选

form 示例：观点 方法 案例 数据 工具 串推 长文

use 示例：可引用 待试 反对 背景 素材

这样“一篇讲 LLM 评估方法、我想拿来试”不需要新标签 LLM评估实践指南，而是 topics=llm,评估 + form=方法 + use=待试。

2. 提示词怎么写才不会发明新类

有效约束是 枚举 + 强制 JSON + 禁止项，不是“请尽量使用现有标签”。

入库时只让模型填这些字段：

text
Copy
Copied
你只能从下列标签中选择，禁止创造新标签，禁止同义改写。
选不出就留空，把 uncertainty 设为 true。

topics（1–3个）：[llm, 投资, 设计, 健康, 写作, 工程, ...]
form（恰好1个）：[观点, 方法, 案例, 数据, 工具, 串推, 长文]
use（恰好1个）：[可引用, 待试, 反对, 背景, 素材]

输出严格 JSON：
{"topics":[],"form":"","use":"","why":"","uncertainty":false}

再加两条硬规则：

词表里没有足够接近的项 → uncertainty: true，topics 可以为空
专有名词、人名、产品名 不是标签，放到 entities（自由文本，不参与分类治理）

人名、书名、项目名变化很快，不该进稳定词表。否则词表会被“某模型名 / 某作者”撑爆。

3. 程序必须拦一道，不要相信模型自觉

把模型输出当不可信输入：

text
Copy
Copied
收到 tags
 → 小写 / 去空格 / 全角转半角
 → 查 alias 表（“大模型”→ llm，“人工智能”→ llm）
 → 不在合法集合里的全部丢弃
 → topics 超过 3 个则只留分数最高的 3 个（或直接截断）
 → 若 topics 被清空，则 status=inbox，等每周人工看
 → 只有通过校验的标签才写入数据库

这一步比提示词重要。模型永远会偶尔输出 AIGC、生成式AI、agent工作流。你要做的是让这些东西 进不了库。

别名表是词表的“泄压阀”。每月把被丢弃次数最高的非法标签看一眼：

出现 10 次以上、含义稳定 → 加进正式词表，或并入已有标签
只出现一两次 → 继续丢弃
其实是实体（人/产品） → 改写入 entities，永不升格为标签

这样词表只在你点头时变，不会每次调用都漂移。

4. 词表怎么设计才“少而稳”

用这套标准收标签，比追求“分得准”有用：

能进词表

未来 6 个月你还会反复用来筛选
能单独当过滤器（只看这个标签也有意义）
和其他标签重叠不超过一半

不能进词表

文章标题里的临时主题
程度词：重要 深度 最新（用 score / 日期）
来源：推特 公众号（用 source 字段）
过细的技术名词：RoPE KV cache（用全文检索或 entities）
互斥大类里的小变体：同时有 AI 和 LLM 和 GPT 就该合并

一个简单测试：

如果这个标签一年只用不到 5 次，删掉。

个人库里的死标签会教模型继续发明近亲。

起步不必完美。先写 15 个你确定会用的主题，跑两周，再按“被丢弃的非法标签排行”扩 5–10 个。不要第一天就设计 80 个。

5. 给旧数据回填时尤其要锁死

历史摘要回打标签时，模型最爱创造新类，因为材料杂。做法是：

每次只送 一小批（20–50 条）
词表附在每一次请求里，不要假设它还记得上次
回填结果先写到临时列 topics_raw，校验后再进正式列
对 uncertainty=true 的条目不要自动“猜一个最接近的”，放着等你扫

“猜最接近”看起来省事，短期会把错误标签写满全库，以后更难收。

6. 治理节奏：标签是配置，不是内容

把词表当成代码配置，而不是数据库里随便插入的值。

合法标签、别名、维度，放一个 taxonomy.yaml / 一张 tags 表（带 active 开关）
条目表只存 tag id，不存自由字符串
停用标签用 active=false，已有条目可保留，新条目不能再选
合并标签是一次 UPDATE，不是让模型“以后注意点”

每月 10 分钟就够：

列出使用次数 = 0 的标签 → 停用
列出近 30 天被丢弃最多的非法词 → 合并或升格
看有没有两个标签经常成对出现且几乎同义 → 合并

如果发现自己每个月都要加很多新主题标签，通常不是世界变了，而是 把实体和形态当成了主题。

7. 最小可用词表模板

你可以先复制再删减，不要先扩张：

topics（多选 1–3）

llm 工程 产品 设计 写作 投资 健康 心理 管理 媒体 法律 教育 历史 科学 城市 生活

form（单选）

观点 方法 案例 数据 工具 串推 长文

use（单选）

可引用 待试 反对 背景 素材

绝大多数 X 帖子用这套都能标完。标不完的，优先 uncertainty，不要新开 prompt工程实战2026 这种标签。

一句话收束：模型负责建议，词表负责存在，校验负责真相。 谁都可以“发明”，但只有你改配置文件时，发明才能变成标签。
